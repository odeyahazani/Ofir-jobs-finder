# הפעלת איסוף והרחבה הדרגתיים

## עדכון האתר הקיים

הריצו ב־Supabase SQL Editor את כל `supabase/upgrade-growth.sql`. זהו שדרוג מצטבר: הוא משמר את כתובת החשבון המורשה, החברות, המשרות, הסימונים והיסטוריית ההתראות. אין צורך להחליף בו כתובת מייל או להריץ מחדש את קובץ ההקמה הראשוני. הוא יוצר תיבת ממצאים ממתינים, העדפות מעקב ופונקציות מוגבלות לייבוא ולניהול מעקב. גם הטבלאות החדשות מפעילות RLS. האתר הקיים ממשיך לפעול אם השדרוג עדיין לא הוחל; מסך הייבוא יודיע שחיבורו לא הושלם.

לאחר פריסת הקוד העדכני, הוסיפו חברות/ממצאים דרך „ייבוא ממצאים”. ניתן להזין קישור קריירה לחברה קיימת שחסר לה קישור באמצעות ייבוא אותה חברה שוב; מקור שכבר הוגדר וסימונים קיימים אינם נדרסים. הסורק אינו מתייחס להצהרה חיצונית על ציון/אימות כראיה. משרה מיובאת מוצגת כממתינה לאימות וקישור לרשומה שנאספה ייווצר רק אחרי התאמה למשרה שאומתה במקור הרשמי.

## הגדרת GitHub Actions

Repo → Settings → Secrets and variables → Actions:

1. תחת **Variables**, הגדירו `NEXT_PUBLIC_SUPABASE_URL` לכתובת הפרויקט.
2. תחת **Secrets**, הגדירו `SUPABASE_SERVICE_ROLE_KEY` למפתח service_role מהלשונית Legacy API Keys של Supabase. זהו מפתח מנהל של עובד האיסוף בלבד; אין להזינו בצ׳אט, בקוד או ב־Vercel. הוא שונה מהמפתח הציבורי שמשמש את האתר.
3. Actions → **Job collector** → **Run workflow** → `check`. ודאו הצלחה.
4. הפעילו `scan`. זו הרצת איסוף אמיתית שכותבת לענן. בדקו משרות בלשונית „כל המשרות” ואת מצבי החברות. „מומלצות” כוללת רק משרות שעברו סינון ואימות וציון 70 ומעלה. אפס המלצות אינו אפס רשומות, וכישלון מקור אינו אפס משרות.
5. להפעלה הדרגתית, הגדירו Repository Variable בשם `ENABLE_SCHEDULED_SCANS` עם הערך `true`. כאשר המשתנה חסר, הרצות התזמון מדולגות. אין צורך במפתח טלגרם לסריקות.

התזמון מכוון להרצות באזור 08:17 ו־17:17 לפי שעון ישראל, כולל התאמה אוטומטית לשעון קיץ/חורף. GitHub Actions הוא שירות תזמון במאמץ מיטבי וייתכנו עיכובים או דילוגים; בדקו את היסטוריית ההרצות. ארבע הפעלות UTC מתוכננות, שמתוכן שתיים מבצעות עבודה לפי השעה המקומית ושתי האחרות מסתיימות ללא גישה לנתונים. בכל הרצה פעילה:

- נבחרת לכל היותר חברה אחת נוספת עם מקור נתמך והתאמה לאופיר, מתוך החברות שכבר קיימות במאגר.
- נסרקות עד 20 חברות, לפי אלה שטרם נבדקו ולאחר מכן לפי הבדיקה הישנה ביותר. במאגר גדול, לא כל החברות נסרקות בכל הרצה; המכסה נועדה לשמור על צריכת משאבים מוגבלת.
- חברות שהמשתמש השהה אינן מופעלות מחדש על ידי ההרחבה האוטומטית. אפשר להפעיל מעקב ידנית במסך החברות.
- נבדקים בנוסף עד חמישה קישורי משרות ממתינים לפי הנתונים המובנים בדף הרשמי; פרטים מאומתים נשמרים ומדורגים בנפרד מטקסט הייבוא. ממצאים גם מקושרים לרשומות מאומתות כאשר קיים קישור קנוני תואם באותה חברה. מקורות לא נתמכים/חסומים נשארים מסומנים כך.

הרצה ידנית `scan-and-expand` בודקת את ההרחבה בלי להפעיל תזמון קבוע. תהליכים חולקים קבוצת concurrency כדי למנוע התנגשויות. אל תריצו במקביל עובד איסוף ממחשב אחר.

## המשימה המתוזמנת בצ׳אט

הוראות לפורמט משותף נמצאות ב־`docs/chat-task-output.he.md`. אפשר להשתמש במשימה הקיימת לגילוי חברות ומשרות, ובסורק לאיסוף ולאימות. אין חיבור אוטומטי מוכח ממשימת הצ׳אט לאתר. עד שיאומת חיבור מורשה, מעתיקים את ה־JSON או מעלים את הקובץ למסך הייבוא. לא מוסיפים סודות להוראות המשימה.

## הנתונים המקומיים הקיימים

בעבודה דרך SQL Editor מומלץ להפריד לשני שלבים: קודם להריץ את כל `supabase/upgrade-growth.sql` מתצוגת Raw, ללא קטע מסומן בעורך; לאחר מכן להריץ את קובץ הנתונים הפרטי `cloud-bootstrap-data-only.sql` שנוצר ב־`.local/`. הוא כולל רק קריאות לפונקציות, ואינו מגדיר פונקציות חדשות. ההפרדה עוזרת לזהות העתקה או הרצה חלקית של קובץ גדול. אין להעלות את קובץ הנתונים לריפו.

הנתונים שכבר נאספו בסביבת הפיתוח נשמרו שם; עצם פריסת האתר אינה מעבירה אותם לענן. לאחר הגדרת עובד איסוף מאומת, אפשר להעביר אותם בפקודת `python -m collector.cloud migrate --sqlite .local/ofir.sqlite`. הפקודה משתמשת בהגדרות המאובטחות של המחשב שמריץ אותה, ומעתיקה גם ממצאים והעדפות מעקב ראשוניים תוך שמירת המידע שכבר קיים בענן. לאחר מכן יש לרענן בסריקה אמיתית. הפעלת scan בענן גם יכולה למלא אותו מחדש מהמקורות, בלי להשתמש במסד המקומי. אין לשמור מסד נתונים או מפתח מנהל בריפו.

הודעות טלגרם נפרדות מהסריקות; התזמון החדש אינו שולח הודעות. נגדיר אותן אחרי ייבוא היסטוריית המועמדויות ובדיקת האיסוף.
